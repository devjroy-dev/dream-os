## §3 · F-44.92: THE THREE DERIVATIONS, NOW DESIGN

### (a) NOTHING IN THE ESTATE ENFORCES THAT A HANDOVER DATE FALLS BEFORE THE WEDDING

Derived at this tip, read line by line. `computeSchedule` (packageSchedule.js:89 to :91) does exactly
two things with a handover package: it tests `isDateKey(delivery_on)` and, passing, assigns
`deliveryOn = delivery_on` verbatim. `isDateKey` (:32 to :36) tests ONLY that the string is a real
`YYYY-MM-DD` that round-trips. The route's own check (leadPackages.js:149) is the same `isDateKey`
and nothing more. There is no comparison against `wedding_date` anywhere on either path.

SO: a handover date in 1999, or fifty years out, or after the wedding, is accepted and written today,
by the app's own sheet as much as by anything else. The seed copy calls it *"the handover date,
before the wedding"* (`packageSeedParse.js:86`), so BEFORE is the product's intent and the estate
holds no mechanism for it. That gap is the app's, not the door's.

WHAT THE DOOR DOES: **the door enforces nothing the estate does not.** It passes what she said and
refuses only what `resolveSpokenDate` refuses, plus the one door rule already ruled for the wedding
date. Concretely: `resolveSpokenDate(date_as_spoken, { direction: 'future' })`, FUTURE because a
handover is ahead of today; an unreadable date takes B7; a resolved date strictly before today in
IST or outside F-44.66's year range takes B21, which is his and already covers "a date that cannot
be right". A handover date AFTER the wedding is NOT refused by the door, because refusing it would
make the door stricter than the sheet she would otherwise use, and R-43.16's estate-wide shape is

### (b) WAY (iii)'s RULE, MADE MECHANICAL, AND WHETHER IT HOLDS AGAINST THE EAR'S ONE DATE SLOT

The rule, as the chair set it: a date on the ATTACH act is used as the handover date ONLY when the
lead's package is a handover package AND that date differs from the lead's wedding date; a date equal
to the wedding date is treated as misheard and the question is asked.

IT HOLDS, and here is why, derived from the schema. `EAR_TOOL`'s `date_as_spoken` is a property of
EACH ACT in `acts[]`, not of the request (listenerDoor.js, the act item's properties). So a lead act
and an attach act in one message each carry their own slot, and `normaliseRequest` keeps both
independently. "Add a lead for Sharma, wedding 5 December, attach the bridal lehenga, handover on
20 November" gives the lead act "5 December" and the attach act "20 November", and nothing in the
door has to guess which is which.

THE FAILURE MODE THE RULE IS FOR, and it is a real one: the listener has been seen copying the
wrong thing into a per-act slot (P1's table: C2 returned "Khanna wedding" into `client_as_spoken`
for Khanna, and row 23 put "Personal" there for a blocked day). So the attach act's date may simply
be the wedding date repeated. The equality test catches exactly that case and costs one comparison.

SO THE DESIGN, under R-44.34 (b), is ASK with a pre-check that avoids asking when she already said
it: if the package resolves to `delivery_basis = 'handover'`, and the attach act carries a
`date_as_spoken` that resolves, and the resolved day is NOT equal to the lead's `wedding_date`, the

across on the thread, exactly as §1.3(a)'s nameless lead does. A cell pins the equality branch: an
attach act whose date equals the wedding date must ASK, never attach, and a mutation removing the

```sql
-- BLOCK 0 · SCHEMA WITNESS. EXPECT one row per column named below, 25 rows on the estate as the
-- plant has it. engine.messages.room was added by 0159 and is ABSENT from the engine doc, which is
-- a FLOOR at ladder 0129 (F-44.51, F-43.13): this block TESTS for it rather than assuming it.
-- If a column you expect is missing here, BLOCKS 1 to 3 are not evidence.
select table_schema, table_name, column_name
from information_schema.columns
where (table_schema, table_name) in
      (('engine','messages'),('engine','conversations'),('engine','agents'),('engine','users'),
       ('public','users'),('public','vendors'),('public','vendor_packages'))
  and column_name in ('id','conversation_id','role','meta','room','agent_id','user_id','auth_user_id',
       'phone','tier','vendor_id','delivery_basis','delivery_days','seeded_from','deleted_at')
order by 1, 2, 3;
```

```sql
-- BLOCK 1 · THE CONTROL. Read this BEFORE block 2.
-- heard_rows is every row carrying meta.listener. joined_rows is the same rows after the identity
-- join. IF joined_rows > heard_rows THE JOIN FANNED OUT (a user carrying more than one vendor row)
-- and block 2's split is NOT evidence. tier_resolved + tier_unresolved must equal heard_rows exactly.
with heard as (
  select m.id, c.agent_id
  from engine.messages m
  join engine.conversations c on c.id = m.conversation_id
  where m.meta ? 'listener'
),
tiered as (
  select h.id, v.tier
  from heard h
  left join engine.agents  a  on a.id = h.agent_id
  left join engine.users   eu on eu.id = a.user_id
  left join public.users   pu on pu.auth_user_id = eu.auth_user_id
  left join public.vendors v  on v.user_id = pu.id
)
select (select count(*) from heard)                                    as heard_rows,
       (select count(*) from tiered)                                   as joined_rows,
       (select count(*) from tiered where tier is not null)            as tier_resolved,
       (select count(*) from tiered where tier is null)                as tier_unresolved,
       (select count(*) from engine.messages where role = 'assistant') as assistant_rows_all;
```

```sql
-- BLOCK 2 · THE ACTS COUNT. Every act the listener heard, split by act, route, lane, model and the
-- vendor's tier TODAY. The identity join is vendorIdentity.ts's, in reverse:
-- engine.agents.user_id -> engine.users -> auth_user_id -> public.users -> public.vendors.
-- A heard row whose request carried NO acts (route 'none') appears as act '(no acts)', so these rows
-- sum to the acts heard PLUS the empty requests, never to heard_rows.
with heard as (
  select m.id,
         m.meta->'listener'                                as l,
         m.meta->'listener'->>'lane'                       as lane,
         m.meta->'listener'->>'model'                      as model,
         m.meta->'listener'->'request'->>'route'           as route,
         c.agent_id
  from engine.messages m
  join engine.conversations c on c.id = m.conversation_id
  where m.meta ? 'listener'
),
tiered as (
  select h.*, v.tier as tier_today
  from heard h
  left join engine.agents  a  on a.id = h.agent_id
  left join engine.users   eu on eu.id = a.user_id
  left join public.users   pu on pu.auth_user_id = eu.auth_user_id
  left join public.vendors v  on v.user_id = pu.id
)
select coalesce(act.value->>'act', '(no acts)')  as act,
       coalesce(t.route, '(no route)')           as route,
       coalesce(t.lane, '(no lane)')             as lane,
       coalesce(t.model, '(no model)')           as model,
       coalesce(t.tier_today, '(unresolved)')    as tier_today,
       count(*)                                  as turns
from tiered t
left join lateral jsonb_array_elements(
       case when jsonb_typeof(t.l->'request'->'acts') = 'array'
            then t.l->'request'->'acts' else '[]'::jsonb end) as act(value) on true
group by 1, 2, 3, 4, 5
order by 6 desc, 1, 2, 3, 4, 5;
```

```sql
-- BLOCK 3 · HER PACKAGES BY DELIVERY BASIS (F-44.92's size on the live estate).
-- live_rows counts packages a vendor can still attach; vendors_with counts how many vendors hold at
-- least one. all_rows is the control: live_rows + retired_rows must equal all_rows on every line,
-- or the filter is wrong and this block is not evidence.
select coalesce(delivery_basis, '(null)')                                    as delivery_basis,
       count(*) filter (where deleted_at is null)                            as live_rows,
       count(*) filter (where deleted_at is not null)                        as retired_rows,
       count(*)                                                              as all_rows,
       count(distinct vendor_id) filter (where deleted_at is null)           as vendors_with,
       count(*) filter (where deleted_at is null and seeded_from is not null) as live_seeded
from public.vendor_packages
group by 1
order by 2 desc, 1;
```
